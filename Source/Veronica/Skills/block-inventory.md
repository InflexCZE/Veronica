---
name: block-inventory
description: Use when a block should store items, or its inventory should hold more, accept other items or connect to conveyors, one create-block just made or one that already exists; it does not create the block: a new one starts with create-block.
---
Needs:
- the block: its prefab binding or any of its files
- which inventory, on a block with several: named by the skill that activated this one, otherwise the user's choice
- capacity: the most mass it holds, in kg
- what it accepts: every item, or only some; items another skill named (a fuel, a recipe's ingredients) must be accepted, and are not asked again
- whether it connects to conveyors, and the conveyor ports: how many and on which faces, the user's choice for their model; their spots from the block that already uses the model, or the user positions them in the Editor

Plan:
- Read the block's components: note which storage parts it already has and which are missing
- Get from the user what this needs and no skill named: capacity, what it accepts, conveyors and ports, and a folder when new files are made
- Set up the inventory: the InventoryComponent and its InventoryDefinition, with its capacity
- Set what the inventory accepts
- Set up the conveyor connection when the user wants it: the ConveyorComponent, and one port dummy per conveyor port, placed by copying or by the user; read them back
- Show the block

Steps:
1. read(block) lists its components: type, sides, tags, definition. A block made from a storage template already has an InventoryComponent and a ConveyorComponent; a block made for another function may have its own inventories (tagged by use, e.g. InventoryInput) or none. Read each InventoryDefinition this works on and read(BlockModelComponentDefinition, "Dummies").
2. Ask the user, with ask_user, for what the Needs list and neither the block nor the activating skill settled: the capacity, what it accepts, whether it connects to conveyors and how many ports on which faces, and a folder for new files. Values left from a template were not chosen for this block. A vanilla block's ports fit its own model, not the user's. For a new model, say they will place the ports in the Editor.
3. Inventory: a missing InventoryComponent: component_add(block, "InventoryComponent"); the BlockPermissionsComponent every block with an inventory needs comes with it. Its definition: the block's own when it has one; otherwise a vanilla storage block's InventoryDefinition as it is, or a create_partial copy of it when values differ. A definition the block does not own is copied first (create_partial(<it>, "copy", folder), then written to the inventory component). MaxMass is the capacity in kg.
4. What it accepts, on the InventoryDefinition: an item goes in only when its Type is in WhitelistedTypes and, when WhitelistedItems is not empty, the item is listed there. Validation checks only the types, so an item missing from WhitelistedItems passes validation and is never accepted. For each item that must go in and is not accepted: element_add(def, "WhitelistedItems", <item>), and its Type in WhitelistedTypes when missing.
5. Conveyors: missing, component_add(block, "ConveyorComponent", "AutogeneratedConveyorComponent"). That definition is shared by storage blocks: the conveyor network connects only at the block's port dummies.
   A port is a dummy whose Type is UseConveyor in the BlockModelComponentDefinition's Dummies: a flat box facing out along its Z, with equal X and Y scale. Keep the ports there; for each port more, element_add(def, "Dummies"), then write its Name and Type only. Positions: for a model another block uses, copy the Transform and Scale of that block's ports; for a new model, the user places them: never compute positions. Then show(the block), ask the user to check or move them (name the paths, e.g. Dummies[1].Transform) with wait_for_user, read(def, "Dummies") again and mark the item with the positions and scales read back.

Show:
show(block). Ask the user to check the ports in the Render View.
