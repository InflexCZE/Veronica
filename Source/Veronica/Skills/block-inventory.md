---
name: block-inventory
description: Use when a block should store items, one create-block just made or one that already exists; it does not create the block.
---
Needs:
- the block: its prefab binding or any of its files
- capacity: the most mass it holds, in kg
- whether it connects to conveyors

Plan:
- Read the block's components: note which storage parts it already has and which are missing
- Get from the user what this needs: capacity, conveyors or not, and a folder when new files are made
- Set up the inventory: the InventoryComponent and its InventoryDefinition, with every value fitting what the user wants
- Set up the conveyor connection when the user wants it: the ConveyorComponent, and one port dummy per conveyor port, placed as the place-dummies reference says; read them back
- Show the block

Steps:
1. read(block); the block-components reference says how to read it, add a component and pick its definition. A block made from a storage template already has an InventoryComponent and a ConveyorComponent; a block made for another function has neither.
2. Ask the user for the capacity, whether it connects to conveyors, and a folder for new files, with wait_for_user.
3. Inventory: add or fill the InventoryComponent and its InventoryDefinition as the block-components reference says. The InventoryComponent goes to the server only, where items live. MaxMass is the capacity in kg.
4. Conveyors: missing, component_add(block, "ConveyorComponent", "AutogeneratedConveyorComponent"). That definition is shared by storage blocks: the conveyor network connects only at the block's port dummies.
   A port is a dummy whose Type is UseConveyor: a flat box facing out along its Z, with equal X and Y scale. Keep the ports there; add one for each port more. Place them as the place-dummies reference says, then mark the item with the positions and scales read back.

Show:
show(block). Ask the user to check the ports in the Render View.
