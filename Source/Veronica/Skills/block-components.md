---
name: block-components
description: Reference: how a block's function is made of components, and how to add one or fill its definition.
---
What is on the block:
read(block) lists its components, one line each: type, sides, tags, definition. A template brings the components of its own function with generated definitions; a block made for another function lacks them. Fill what is there and add what is missing. One component does one job on a block; component_add refuses a type whose job another component already does.
A comparable vanilla block shows which components and values a function uses: read(its prefab binding), then its definitions.

Adding a component:
component_add(block, type, definition?) puts it on the sides its type needs and adds the components it depends on. The reply names each component still without a definition; the block fails validation until each has one.

Its definition, by what the user wants:
- The block has its own (generated by its template, or made in the mod): read it, and write the values that do not fit what the user wants. It stays the component's definition; pointing the component elsewhere leaves the block's own file unused.
- None yet, and the user wants an existing block's values as they are (vanilla or another mod's): point the component at that block's definition, with component_add's definition or write(block, "Components[<type>].Definition", <it>).
- None yet, and some values differ: create_partial a copy of the closest existing definition, write the values that differ, and point the component at the copy. With nothing close, create_definition and write every value.
- A change to a definition the block shares with vanilla goes on a create_partial copy, and the component is pointed at the copy.
